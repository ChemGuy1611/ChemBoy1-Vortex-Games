# Vortex Extensions Feed

Reference copy of Nexus Mods' public extension catalog, `GET https://api.nexusmods.com/v3/vortex/extensions`, plus an explanation of how extensions reach that feed and how Vortex uses it. The raw response is saved next to this file as `vortex-extensions-feed.json`. Endpoint parameters, schema and stability tier are in `NEXUS_MODS_API.md`; Vortex's side of the integration is in `VORTEX_NEXUS_INTEGRATION.md`.

The tables in the Snapshot section are generated, together with the JSON, by `refresh_extensions_feed.py`; the rest of this file is hand-written. The Snapshot table is what an API audit reads to decide whether the copy is stale. The endpoint needs no API key and costs no rate limit, so an audit can simply re-fetch it and compare.

## Refreshing the snapshot

Run `python refresh_extensions_feed.py` from the repository root (`--dry-run` previews the tables without writing). It overwrites `vortex-extensions-feed.json` with the live response, in the pretty-printed form `oxfmt --check` accepts, and rewrites the generated tables in the Snapshot section above, including the fetch time. It also lists the `game-*` folders that have no ChemBoy1 game row. The rest of this file is hand-written, so after a refresh re-read the explanations and the Observations section against the new figures. A change in the `other` count, in the number of distinct `game_id` values, or in the set of fields per row is worth a note in `NEXUS_MODS_API.md`.

## How an extension gets into the feed

Each statement is tagged by how well it is established. **Documented** means the OpenAPI spec or the Vortex source says so. **Observed** means it was checked against live data on the fetch date above. **Unknown** means neither.

1. **Publishing.** A Vortex extension is an ordinary mod page on Nexus under the `site` game (`nexusmods.com/site/mods/<mod_id>`).
   - Observed: every extension page checked (mods 112, 431, 946, 1063, 1319 and 2381 by ChemBoy1, both `game` and `other` ones, and mod 244 by another author) is published and in Nexus category 4. The retired Vortex-Backend generator mapped Nexus categories 4, 7 and 13 to game extension, translation and theme.
   - Unknown: whether the category is what admits a mod page to the feed.
2. **What a row contains.** Documented: the row is forwarded from the mod page, and uniqueness is `mod_id` plus `file_id` (one mod per extension, one file per version).
   - Observed: a row's `file_id`, `version` and `uploaded_at` equal the mod's current MAIN file, exactly, on all five checked pages that have a row (mods 112, 244, 431, 1319 and 2381). Older files, which Nexus flags ARCHIVED, never appear.
   - Consequence: uploading a new MAIN file is what changes the row, and `version` is that file's version string.
   - Observed: the feed is a cached snapshot, not live. After a bulk upload of 274 new MAIN files, more than an hour after the first of them, only 8 rows had changed and the rest still showed the previous version, while the v1 file list for every one of the 274 already showed the new MAIN file. To confirm an upload landed, read the mod's file list (`GET /v1/games/{domain}/mods/{id}/files.json`), not the feed.
3. **Classification.** Documented: Nexus analyses the extension's code (`info.json`) on the server. If it targets one game the row is `type: "game"` with that game's numeric Nexus id in `game_id`; otherwise it is `type: "other"` (helpers, dependencies and global patchers end up here). Themes and translations are separate lists, and translations carry a `locale`.
   - Unknown: how themes and translations are recognised. The retired generator used mod categories 13 and 7.
4. **One extension per game.** Documented in the Vortex source: the API already de-duplicates game extensions, and Vortex re-checks on its side, keeping the newest `uploaded_at` per `game_id`.
   - Observed: the 2026-10-17 snapshot has 602 `game` rows and 602 distinct `game_id` values, so no game appears twice.
   - Observed, resolved: until the 2026-10-01 snapshot the feed listed mod 244 (uploaded 2021-07-03) for game 2433 (State of Decay 2) and had no row for ChemBoy1's mod 946, which was published, in category 4, and last uploaded 2026-09-27. The mod was missing entirely rather than listed as `other`, so it was not a classification result. It was reported to Nexus staff as an error; by the 2026-10-10 snapshot the feed lists only mod 946 for game 2433 and mod 244 is gone. The cause was never established.
   - Observed: game 4309 (Sifu) lists mod 350 and has no row for ChemBoy1's mod 1063. That one is deliberate: Nexus staff rejected that extension change, so the slot is held on purpose.
   - Unknown: the server's tie-break rule when two extensions claim the same game. Vortex applies "newest upload wins" on its own side. The one unexplained case (State of Decay 2) kept the older mod until staff changed it, but it was treated as an error, so it is not evidence of an intended rule.
5. **No manual step is documented.** Before Vortex 2.7.0 a maintainer had to add each new extension by hand: the Vortex-Backend repository's "Add Extension" workflow took the mod id, the type and (for games) the game domain, and a daily workflow refreshed versions and download counts, dropped hidden or deleted mods, and committed `out/extensions-manifest.json`. Its last commit is 2026-09-08. The v3 endpoint documents no equivalent step.
   - Unknown: how long a new upload takes to appear. This was not measured. The response sends `Cache-Control: max-age=0, private, must-revalidate` with a weak `ETag`, so no HTTP cache delay is declared.
   - Unknown: how hidden, deleted or unpublished mod pages are handled.

## How Vortex uses the feed

Vortex 2.7.0 and later, checked against the master source on the fetch date. Up to 2.6.x Vortex read the `extensions-manifest.json` published by the Vortex-Backend repository and cached it in its `temp` folder; it no longer writes that file.

1. **Fetch.** Once per session, at startup, Vortex downloads the feed and the Nexus game list (`nexus_gamelist.json`) in parallel. The result is memoised for the session. The Extensions page refresh and the browse dialog force a new fetch. Nothing is fetched while offline.
2. **Mapping.** Each row becomes a catalog entry. A `game` row keeps its numeric `gameId`, which Vortex resolves to a domain name and a game name from the local game list. An `other` row has no game. Themes and translations are typed accordingly. Rows whose `mod_id` or `file_id` is not a number are dropped. Vortex then keeps one game extension per game id, the one with the newest `uploaded_at`.
3. **Browse and install.** The Extensions page lists the catalog. Installing downloads the entry's `file_id` from Nexus into the `site` download folder and installs it; a restart is needed afterwards. An `nxm://site/...` link that carries a file id does not need the catalog, while one with only a mod id gets its file from the catalog. At install time Vortex records the catalog entry's `modId`, `fileId` and `version` on the installed extension. An extension installed without a catalog entry has no recorded `modId` unless it can be restored (see step 4).
4. **Automatic updates.** After every fetch, Vortex pairs each installed extension with the catalog entry that has the same `modId`. When the catalog's version is higher than the installed one (both parsed with `semver.coerce`), Vortex downloads and installs it, removes the older version, shows a notification and asks for a restart. Three consequences follow. An extension with no recorded `modId` is not updated by this step. A version string that does not parse as semver is skipped. A new file whose version is not higher never triggers an update.
   - **Restoring a missing `modId` (Vortex 2.8.2 and later; not in 2.8.0 or 2.8.1).** Vortex 2.7 stopped reading `modId` from an extension's `info.json`, so extensions installed by an older Vortex lost their link to the catalog and stopped updating. 2.8.2 reads `modId` again, for that purpose only: when an installed extension has no `modId` in Vortex's state and its `info.json` holds a positive whole number, Vortex stores it. Any other value is ignored and leaves the extension unlinked rather than failing to load.
   - **Offering a link (2.8.2 and later).** For game extensions that still have no `modId`, Vortex looks at the Nexus domain of the games each one registers. If the catalog holds exactly one game extension for that domain, it is a different mod from every installed one, and its version is higher than the installed version, Vortex asks the user to confirm linking the two. Accepting stores the catalog's `modId` and installs the newer version. Declining stores `nexusLinkDeclined` on the extension so it is not offered again. Each candidate is offered at most once per session, and bundled extensions and ones marked for removal are skipped. The match is a guess from the game's domain, which is why the user confirms it.
   - Observed on the fetch date: this repository's extensions carry `id`, `gameId`, `modId`, `name`, `author`, `version` and `description` in `info.json`, with `modId` kept equal to the mod id at the end of the extension's `EXTENSION_URL` (the `"XXX"` placeholder of an unpublished extension is ignored by Vortex). So the restore above applies to them and the by-game-domain offer is only a fallback. Vortex does not read `gameId` from `info.json`; the game id it uses comes from the feed row's `game_id`.
5. **Dependencies.** An extension's declared dependency is looked up in the catalog and installed on demand.
6. **Site installer.** Archives for the `site` game cannot be installed from the mod list; Vortex tells the user to use the Extensions page.
7. **Error report link.** An error dialog raised by an extension offers a Report link to `nexusmods.com/site/mods/<modId>?tab=bugs`. The mod id comes from the extension's own `info.json` `modId` (read again since 2.8.2; before that only the catalog entry could supply it) and otherwise from the extension's catalog entry. The host is always `site`, so an extension whose mod page lives on a game domain (`bloodborne` here) gets a wrong link.

## What this repository does with it

- `patch_extensions.py` fills unset `EXTENSION_URL` constants with `https://www.nexusmods.com/site/mods/<mod_id>`. It fetches the feed live through `load_vortex_manifest()`, keeps the rows whose `author_user_id` is ChemBoy1's, and maps `game_id` to a domain with `nexus_gamelist.json`. It does not read the saved JSON.
- For an audit, the saved copy supports a cross-check without any per-mod API calls: compare each ChemBoy1 row's `version` with the extension's `info.json` to see what is live, and look for `game-*` folders that have a published `EXTENSION_URL` but no ChemBoy1 feed row (the State of Decay 2 case above while it lasted, or a deliberate staff decision such as Sifu).

## Observations

Hand-written against the 2026-10-22 snapshot; re-check after a refresh.

- 275 of the 289 `game-*` folders have a ChemBoy1 `game` row. The other 14 are:
  - 11 with no published extension (`EXTENSION_URL` unset, empty or absent): seven games have no feed row at all, and four (`reddeadredemption2`, `starwarszerocompany`, `subnautica2`, `thebloodofdawnwalker`) have a row owned by another author.
  - `gzdoom`, which does have a ChemBoy1 `game` row (mod 1319, `game_id` 1839, uploaded 2026-10-16; 1839 is the `doom1993` game page). The refresh script lists it anyway because it looks the folder name up as a Nexus domain in `nexus_gamelist.json`, and `gzdoom` is not one.
  - `bloodborne`, whose mod page is on the `bloodborne` game domain, not under `site`, so it is not a Vortex-site extension.
  - `sifu`, whose slot is held deliberately because Nexus staff rejected the ChemBoy1 extension change (the feed row is Tannin42's mod 350).
- Two ChemBoy1 rows are new since the 2026-10-17 snapshot: mod 2467 (Over the Hill) and mod 2472 (Apocalypter).
- `stateofdecay2` moved out of this list since the 2026-10-01 snapshot: its feed row is now ChemBoy1's mod 946.
- ChemBoy1's two `other` rows are the RE Engine wrapper (deprecated) and the global ignore patterns helper. The UZDoom extension, `other` in the 2026-10-10 snapshot, is now a `game` row.
- Feed size grew from 704 to 719 extensions between 2026-10-10 and 2026-10-17 (`game` 582 to 602, `other` 122 to 117), and to 725 by 2026-10-22 (`game` 608, `other` still 117); the fields per row are unchanged.
