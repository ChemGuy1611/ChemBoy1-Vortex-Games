# template-rpgmaker Changelog

## [2026-09-28]

- Added: a `license*` glob (`path.join("**", "license*")`) alongside the existing `changelog*`/`readme*` entries in `IGNORE_CONFLICTS`/`IGNORE_DEPLOY`, so LICENSE files are treated the same as README/CHANGELOG - never flagged as a mod conflict, never deployed into the game folder.

## [2026-09-28]

- Added: `context.registerLoadOrder` (FBLO) for the plugins.js array - installed plugins now show up on Vortex's Load Order page, where they can be dragged into a new order or toggled on/off via the `status` field, instead of only ever being appended in install order.
- Changed: `installJsFolder`/`installJsFile` no longer read-modify-write plugins.js at install time. That logic (and its read-modify-write race when two plugin mods install back to back) is replaced by the load order's `deserializeLoadOrder`/`serializeLoadOrder` hooks, which reconcile the file against whatever plugin files are actually deployed to `js/plugins`.
- Fixed: reading plugins.js sliced from the array's `[` to the file's first `;`, which a semicolon inside a plugin's `description`/`parameters` string could hit before the array's real closing `;`. Now slices to the LAST `;` in the file.
- Changed: the setup notification no longer claims plugins.js must be updated manually - it now points at the Load Order page for reordering/enabling and keeps only the still-true note that some plugins need their parameters filled in by hand.
- Added: `installJsFolder`/`installJsFile` now stamp a `pluginNames` attribute listing the plugin basenames they installed. `deserializeLoadOrder` matches it against `persistent.mods` to fill each Load Order entry's `modId`, so core FBLO no longer shows a "Not managed by Vortex" banner on plugins Vortex actually installed.
- Changed: the Load Order page now lists only plugins owned by a Vortex mod (resolved via `modId`) - the game's own vanilla plugins are filtered out of the page entirely. `serializeLoadOrder` still writes them back to plugins.js untouched (in their existing on-disk order) so they're never dropped from the file, and re-reads the file fresh at write time so hand-edited `description`/`parameters` on either vanilla or managed entries survive a reorder/toggle instead of being overwritten by a stale in-memory copy.
- Fixed: purging mods was wiping every plugin's custom `parameters` out of plugins.js. A purge removes every deployed plugin `.js` file, and core FBLO reads the load order (and, on the very next state change, writes it back out) whenever that happens - with no plugin files on disk, that write saw "every plugin uninstalled" and overwrote plugins.js with defaults. A module-level guard now skips both `deserializeLoadOrder` and `serializeLoadOrder` for the duration of a purge (armed on `will-purge`, since core's own did-deploy handling would otherwise read the load order before a listener on that same event could clear it) and re-runs the read/dispatch itself once the purge's matching deploy actually restores the files.
- Added: a per-profile sidecar (`<profileId>_pluginsLoadOrder.json`, in the game's root folder, Vortex-owned and never parsed by the game) now durably stores each managed plugin's full entry (`name`/`status`/`description`/`parameters`) alongside plugins.js itself. `deserializeLoadOrder` prefers plugins.js's own copy of a plugin (catches hand edits) and falls back to the sidecar's copy when plugins.js doesn't have it (e.g. reset by something outside Vortex); `serializeLoadOrder` writes every managed entry to both files. Same pattern as the UE4-5 template's `<profile>_loadOrder.json` PAK sidecar.
- Added: a `customItemRenderer` (`LoadOrderItemRenderer`) and rich `usageInstructions` (`LoadOrderInstructions`) wired into the existing `registerLoadOrder` call, porting the `game-warhammer40kdarktide` FBLO row pattern - mod thumbnails, position locking (`onLock` + explicit `serializeLoadOrder` call, since core's own auto-serialize can miss a lock-only change), status filter pills (enabled/disabled/locked/unlocked/unmanaged, module-level pub-sub via `useFbloState` since core's FBLO page has no context provider to hook into), multi-select (ctrl/shift-click), and a right-click `FbloContextMenu` (enable/disable, lock/unlock, move to top/bottom, open staging folder/mod page, enable/disable the underlying Vortex mod). Adapted for file-granularity plugin entries (`LO_ATTRIBUTE` is array-valued, one Vortex mod can own several plugin files) - no "Open Mod Folder" item, since a plugin file has no per-entry folder of its own the way a mod folder does on darktide; Open Staging Folder / Open Mod Page cover that need instead. `deserializeLoadOrder` now also seeds each entry's `locked` flag from the previously stored load order (falling back to the sidecar's own copy - see below), since plugins.js has no lock field of its own.
- Fixed: the sidecar was dropping `locked` on write - it round-trips the same file-shaped object written to plugins.js, which has no lock concept, so a locked position had no durable copy beyond core's own `persistent.loadOrder` state. `serializeLoadOrder` now writes a derived array to the sidecar with `locked` added back in (plugins.js itself stays unchanged - a Vortex-only field doesn't belong in a file the game parses), matching how the UE4-5 template's PAK sidecar already round-trips its whole entry including `locked`.
- Added: on purge, a new `did-purge` listener calls `clearPurgedPlugins`, which removes the now-dead entries of every purged (mod-owned) plugin from plugins.js while leaving vanilla/still-deployed entries untouched - ported from `game-thelastofuspart2`'s `didPurge`/`clearModOrder` pattern (a dedicated purge cleanup, independent of the reorder/serialize cycle, which stays intentionally no-op'd during a purge by the existing `isPurging` guard). Previously a purge left dead plugins.js entries pointing at deleted `.js` files until the next unrelated reorder/toggle happened to clean them up. The sidecar is deliberately left untouched - it's the recovery copy consulted again if the same plugins get reinstalled.
- Added: an "Edit Parameters" button on each Load Order row (and matching context-menu item) opens a popup text editor for that plugin's `description` and `parameters`, so both can be set without hand-editing plugins.js. The parameters field holds only the inner key/value pairs - wrapping `{}` is optional, one gets stripped off if included and always re-added before writing, so `"key": "value"` and `{"key": "value"}` both work. Quotes are optional too: a bare `key: value` (or several, comma- or newline-separated) is accepted as a fallback whenever strict JSON parsing fails, and both sides get forced into double-quoted JSON strings before writing - matches how RPG Maker MV/MZ itself always stores plugin parameter values (plain strings, even for declared number/boolean/struct types; the plugin's own code casts them at runtime). Writes go straight to plugins.js AND the sidecar via a new `writePluginEntry`, bypassing `serializeLoadOrder`'s on-disk-wins freshness priority entirely (that priority exists to protect a stale in-memory snapshot from overwriting a fresher hand-edit - backwards for an edit arriving FROM this dialog). The popup's initial text is read fresh via a new `readPluginEntry` (same plugins.js-then-sidecar priority as `deserializeLoadOrder`) rather than from the Load Order entry's own cached `data`, which can already be stale by the time the button is clicked. A parse failure (still possible - e.g. an unquoted value containing a comma) reopens the dialog with both the description edit and the user's own typed parameters text preserved rather than discarding either.
- Fixed: pressing Enter inside either multiline field of the Edit Parameters popup submitted/closed the dialog instead of inserting a newline, making multi-line text impossible to type. Vortex core's dialog binds Enter (anywhere in the modal, regardless of focus) to whichever button is marked `default: true`; removing that flag from the Save button (extensions can't reach into core's dialog component to scope the handler to specific fields) stops Enter from being intercepted, at the cost of Save losing its highlighted/primary styling.

## [2026-09-25]

- Changed: `util.opn(...)` (deprecated Bluebird-promise API) replaced with `window.api.shell.openUrl()`/`openFile()` (void, no promise) at every call site, each wrapped in `try`/`catch` reporting failures via `showErrorNotification(..., { allowReport: false })` instead of the old silent `.catch(() => null)`.

## [2026-09-12]

- Fixed: installers scoped their file list to the mod root with `file.indexOf(rootPath) !== -1`, a substring test that silently dropped every extension-less file. `path.dirname()` returns `"."` when the mod file sits at the archive root, which collapses the test to "the path contains a dot", so extension-less payloads never reached the staging folder; the same test also matched sibling folders that happen to share a name prefix. All 4 installers now derive `const rootPrefix = rootPath === "." ? "" : rootPath + path.sep;` and filter with `file.startsWith(rootPrefix)`.
- Added an "Open SteamDB Page" button next to "Open PCGamingWiki Page", opening the game's `https://steamdb.info/app/<STEAMAPP_ID>/` page.

## [2026-09-06]

- Changed: migrated off the deprecated `vortex-api` `fs` wrapper onto native node `fs`. `fs` now means node's own module (`const fs = require("fs")`, plus `const fsp = fs.promises` for the async calls), and the vortex-api wrapper is still imported alongside it as `vfs`. Call sites move across 1:1 - `fs.statAsync` becomes `fsp.stat`, `fs.readdirAsync` becomes `fsp.readdir`, `fs.readFileAsync`/`fs.writeFileAsync` become `fsp.readFile`/`fsp.writeFile`, `fs.renameAsync` becomes `fsp.rename` - while the two that need options change shape: `fs.ensureDirSync(p)` becomes `fs.mkdirSync(p, { recursive: true })` and `fs.removeAsync(p)` becomes `fsp.rm(p, { recursive: true, force: true })`. `fs.copyAsync` becomes `fsp.cp` and always gains `recursive: true`, because native `cp` throws `ERR_FS_EISDIR` on a directory without it.
- Note: `ensureDirWritableAsync` stays on the wrapper as `vfs.ensureDirWritableAsync` - it has no native equivalent, and it is the call that creates a mod folder inside the game install and offers the elevation prompt when that folder is not writable. `vfs.unlinkAsync` is kept for the same reason where it appears. Everything else loses the wrapper's retry-and-elevate handling, which upstream deprecated deliberately; reach for `vfs.forcePerm` if a migrated write turns out to need it.

## [2026-08-10]

- Changed: `hasXbox` is now derived from the active discovery IDs. It is declared with `let` and initialised to `false`, followed by `if (DISCOVERY_IDS_ACTIVE.includes(XBOXAPP_ID)) hasXbox = true;`, so adding the Xbox app ID to `DISCOVERY_IDS_ACTIVE` is enough to switch on the Xbox version logic. Setting the initialiser to `true` still forces it on for games that need it without an Xbox ID in the list.
